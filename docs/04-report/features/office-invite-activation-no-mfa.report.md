# 사업단 등록 계정 활성화 및 MFA 중단 결과

## 구현

- 사업단 구성원과 교내 강사는 대학 이메일(@uc.ac.kr)로만 관리자 수동 등록한다. 등록 시 서버에서 Supabase Auth 계정을 자동 생성하고 구성원과 연결한다. 단회성 허가와 기존 요청 ID를 이용해 중복 및 실패 후 재시도를 처리한다.
- 최초 비밀번호를 알 수 없는 상태로 계정을 만들며, 이메일 복구 링크 확인과 승인된 개인정보 안내 동의, 새 비밀번호 설정 전에는 업무 데이터에 접근할 수 없다.
- 사업단·교내 강사 로그인 아래에 3단계 활성화 안내와 ‘신규 비밀번호 설정’ 버튼을 넣었다. 수강생·교외 강사에게만 공개 가입 옵션을 제공한다.
- 앱의 MFA 이동·안내를 제거하고 DB의 MFA 요구를 중단했다. 기존 계정 활성 상태, 역할, 비밀번호·세션 검사는 유지한다.

## 검증

- 로컬 Supabase Auth: 사업단 계정 생성→복구 이메일 토큰 검증→동의→첫 비밀번호→MFA 없는 로그인 통과.
- 로컬 Supabase Auth: 교내 강사 계정 연결·강사 역할·로그인 구분 통과.
- 구성원 UI·서버 액션 검사 25개, TypeScript, ESLint, 프로덕션 빌드, Git whitespace 검사 통과.
- 설계 대조: `docs/03-analysis/office-invite-activation-no-mfa.analysis.md`, 6/6 일치.

## 운영 적용

- Git 푸시에는 운영 DB migration 적용과 Supabase Auth 설정 변경이 포함되지 않는다. 배포 시 migration, 이메일 인증·복구 메일, MFA 신규 등록 중단 설정을 대상 환경에서 확인해야 한다.
- 실제 수신 메일과 운영 계정으로 하는 첫 로그인 검증은 배포 후 수행한다.

## 운영 후속 점검 (2026-09-29)

- 배포 전부터 등록돼 있던 사업단 구성원 9명은 Auth 계정이 없어 복구 메일을 받을 수 없었다. 대학 이메일, 활성 명부, 계정 충돌을 확인한 뒤 동일한 단회성 nonce 검증 경로로 9명 모두 연결했다. 10명의 대상 구성원 중 9명은 최초 비밀번호 설정 대기 상태이며 기존 1명의 상태는 보존했다.
- 무작위 임시 비밀번호가 Supabase의 대문자·소문자·숫자·특수문자 조건을 우연히 만족하지 못할 수 있어, 모든 조건을 포함하도록 생성 방식을 보완했다.
- `ispark2@uc.ac.kr`의 복구 메일 요청은 Auth API와 Auth 로그에서 HTTP 200을 확인했다. 받은편지함의 실제 수신과 링크 사용·첫 로그인은 사용자 확인이 필요하다.
