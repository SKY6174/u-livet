# 수강료 입금·환불 관리 구현 보고

2026-09-19 · anchor-finance · 로컬 구현·검증 완료

유료 과정 신청에서 납부대기·좌석예약·실제 입금 대사·수강확정을 연결했다. 수강생의 환불 신청에는 수강취소를 함께 반영하고, 담당자의 조항 검토·별도 승인·은행 업무 결과 확인을 나누어 기록한다. 사용자가 답변한 대로 실제 환불·감면 규정은 미확정 상태로 유지한다.

## 메뉴와 흐름

| 이용자 | 메뉴 | 기능 |
|---|---|---|
| 과정담당 | 사업단 관리 → 기수 상세 | 공개 전 수강료·승인 환불 규정·예약시간·납부 안내 설정 |
| 수강생 | 나의 공간 → 나의 납부·환불 | 청구·규정 확인, 입금 신고, 수강취소·환불 신청, 처리 이력 |
| 수납담당 | 수납·환불 `/finance` | 은행 거래 확인, 분할/다중 청구 배분, 미배분 잔액 확인, 환불 조항 검토·산출 |
| 별도 승인자 | 수납·환불 | 산정 근거 확인 후 승인 또는 사유 반려 |
| 지급담당 | 수납·환불 | 은행 업무 시작 기록, 실제 지급/미지급/불명확 결과 대사 |

입금 신고만으로 수강을 확정하지 않는다. 실제 확인된 입금의 배분 합계가 청구를 충족해야 하며, 만료 후 입금은 자동 등록하지 않는다. 무료 과정에는 가짜 입금 원장을 만들지 않는다.

FINANCE 역할에 기관·유효기간·업무별 위임이 추가로 필요하다. 자기 거래 처리, 산출자 자기 승인, 승인자의 자기 지급을 차단한다. 원거래 참조와 배분·청구·환불 예약 한도를 DB에서 확인하며, 지급 결과 불명 시 거래 확인 전 재송금을 시작할 수 없다. 지급 완료와 청구 조정을 함께 저장해 환불 때문에 허위 미납이 생기지 않는다.

## 검증 결과

- **127개 자동 검사 통과**: 기존 90개 + 수납·환불 37개.
- 전체 15개 로컬 마이그레이션 재생, 린트·타입·프로덕션 빌드, 로컬 DB 보안 점검.
- 실제 브라우저에서 수강생/수납담당/별도 승인자 계정을 바꾸어 신고 → 대사 → 배분 → 환불신청 → 산출 → 승인 → 지급 결과 저장 확인.
- 가상 120,000원 반환 후 지급액·청구 조정액이 일치하고 환불 예약·미납은 0원으로 확인.
- 390px 모바일 가로 넘침 없음, 테스트한 세 계정의 브라우저 오류 없음. 마지막 빌드 후 재시작한 홈 화면도 정상 표시.

## 운영 적용 전 필요한 결정

실제 수납 주체, 승인 환불 규정/계산 조항, 개인정보 수집 문안·보유기간, 승인 납부 안내, 수납/환불승인/지급 위임을 등록해야 한다. 기본 환불률·감면률·실제 은행 계좌는 넣지 않았다. 검증용 1/1·2/3·0/1 조항은 기관의 실제 기준이 아니다.

홈페이지는 실제 송금하지 않는다. 전체 계좌번호를 수집하지 않고 기관에서 확인한 원입금자 반환 문서 참조만 기록한다. 원격 DB 적용·운영 배포는 하지 않았다.

미배분·초과입금의 배분 전 반환, 감면·장학금, 확정 원장 정정 UI, 은행/PG 자동 연결, 강사료·세무 증빙, 장기 회계 보고는 후속이다. 관리자 MFA·재인증, 보유/파기, 복구·부하 검증도 운영 전에 필요하다.

다음 권장 단위는 **안내문자 관리**다. 발송 대상/내용 미리보기·운영/홍보 구분·동의 상태·발송 이력을 먼저 구현하고 실제 발송은 선정된 업체와 기관 설정을 연결한다.
