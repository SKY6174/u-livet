# 운영 환경 수료 판정·승인 검증 기수 설계

> Feature: anchor-completion-live-test | 2026-09-25
> Plan: [계획](../../01-plan/features/anchor-completion-live-test.plan.md)

## 격리 구조

기존 두 `life_offerings`는 읽기만 한다. 별도 `life_organizations`(`uc-anchor-completion-review-test`) 아래 검증 연도, 두 과정·버전·기수를 만든다. 기수명과 조직명에 `[검증용]`을 붙이고 `DRAFT` 상태로 두어 공개 과정 목록에 나타나지 않게 한다. 실제 과정과 같은 제목·분야를 사용하되 수료 시험이 가능하도록 검증 기수의 종료일은 이미 지난 날짜로 설정한다.

## 데이터 및 권한

- 검증 조직에만 유효한 모집·수료 정책을 생성한다. 수료 정책의 출석 기준은 80%이며 두 별도 검증 담당자를 작성자·승인자로 기록한다.
- 현재 운영 관리자에게 검증 조직에 한정된 `COURSE_MANAGER`, `CERTIFIER` 역할을 부여한다. 실제 사업단 조직의 권한은 바꾸지 않는다.
- 기수별 합성 수강생 6명에 대해 `life_people` → `life_applications` → `life_enrollments`를 만든다. 계정·연락처·결제 정보는 생성하지 않는다.
- 철회 사례에는 0원·가상 전화번호의 `[검증용]` 환불 신청서 완료 표시를 넣는다. 실제 금융 환불은 만들지 않는다.
- 기수별 종료된 100분 수업 1회와 출결을 만든다. 90%, 85%, 70%, 철회 50%, 확정 100%, 출결 미입력 사례를 구성한다.
- 90%는 승인 가능한 `READY` 판정을 별도 검증 담당자 명의로 저장한다. 85%는 미산출로 두어 UI에서 실제 산출한다. 70%는 `INELIGIBLE`, 철회자는 `NEEDS_REVIEW`, 100%는 승인 완료 판정을 보인다.
- 출결·등록 입력을 끝낸 뒤 운영자료 마감과 판정 레코드를 기록해 `academic_revision` 일치를 유지한다. 판정 근거에는 해당 정책과 출석률을 명시한다.

## 실행 및 검증

`scripts/seed-completion-live-test.sql`은 단일 트랜잭션으로 실행하며 검증 조직 slug가 이미 있으면 중단한다. `scripts/cleanup-completion-live-test.sql`은 동일 slug에 속한 검증 데이터만 역순으로 제거하도록 작성한다. `supabase db query --linked --file`로 적용하고 과정·수강생·출석·판정 수 및 원 과정 불변 여부를 조회한다. 로그인된 관리자 화면에서 85% 수강생 산출, 90% 수강생 승인을 실행한다. 승인 전후 상태와 감사 기록을 확인한다.

## 경계

검증 기수는 모집 공개·증명서 발급·금융 환불·메시지 발송을 하지 않는다. 합성 판정과 승인은 교육 이력으로 사용할 수 없다. 실제 과정의 정책, 출석부, 수료 통계는 변경하지 않는다.
