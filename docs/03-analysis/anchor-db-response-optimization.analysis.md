## 설계 비교

구현 항목 8/8 충족: 학습자 읽음의 과정 범위, 제출물의 과정 범위, 성적의 중첩 과정 범위, 학습자 본인 필터, 기존 선행 권한 검사, 5개 업무 조회 병렬 유지, 관리 화면 독립 조회 병렬화, 조직별 현황 결합·오류 상태 유지.

기존 회귀검사의 mock에 최근 추가된 운영 대시보드·강사 서명 구성요소와 예산 RPC가 빠져 실행되지 않는 문제를 함께 보완했다. 앱의 해당 기능 자체는 수정하지 않았다.

## 네이티브 DB 검증

로컬 PostgREST에 설치된 클라이언트로 3개 관계 필터 요청을 실행하여 정상 응답 및 권한 없는 결과 0건을 확인했다. 실제 데이터가 있는 비교는 별도 SQL 트랜잭션에서 수행했다. 기존 시험 계정의 MFA secret이 없고 공개 가입도 닫혀 있으므로 기존 계정·가입 설정을 변경하지 않았다.

전용 합성 Auth 사용자·세션과 4개 과정, 과정별 과제/제출/성적 각 10건을 만든 뒤 authenticated 역할·합성 JWT claims로 RLS를 적용했다. 강사에게 배정된 3개 과정의 30건만 보였고 미배정 과정은 보이지 않았다. 현재 과정 inner join은 정확히 10건을 반환했다. 이 트랜잭션은 전부 롤백하고 사용자·과정 잔존 0건을 확인했다.

5쌍 교차 실행 중 첫 쌍 제외 4회의 EXPLAIN ANALYZE 실행시간 중앙값이다. JSON 집계까지 포함한 동등 SQL 읽기의 비용이며, 운영 HTTP 또는 로그인 전체 응답시간이 아니다.

| 조회 | 기존 | 개선 | 감소 | 결과 행 | JSONB 텍스트 크기 |
| --- | ---: | ---: | ---: | --- | --- |
| 제출물 | 532.14ms | 215.12ms | 59.6% | 30 → 10 | 151,110 → 51,140B |
| 성적 | 534.33ms | 354.68ms | 33.6% | 30 → 10 | 28,980 → 10,650B |

JSONB 크기는 SQL 직렬화 측정이며 실제 HTTP 전송량과 동일하지 않다. 원격 로그인 전체 속도와 동시 부하는 측정하지 않았다.

## 품질 확인

- 신규 페이지/요청 회귀 10개
- 기존 DB 성능 16개, workspace 8개, 개설 prefill 7개, 임시저장 8개, 역할 메뉴 20개
- 성능 프로브: redirect 10개와 전체 실행 시나리오 4개
- native RLS 비교 및 롤백 확인
- lint, 설명서 확인 및 Next 프로덕션 빌드 통과

Supabase 보안 Advisor에는 INFO인 rls_enabled_no_policy만 있고 ERROR/WARN 항목은 없었다. [정책 없는 RLS 설명](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). 기존 성능 Advisor의 정책·인덱스 권고는 별도 검토 대상으로 유지했다. 스키마·RLS·운영 자료는 변경하지 않았다.
