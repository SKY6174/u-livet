|---|---|

범위 내 설계 대조이며 전체 플랫폼의 완료율로 확대하지 않는다. 미배분 입금 반환/감면/세무/은행 API 등은 계획에 명시한 후속 범위다.

## 검증

전체 15개 마이그레이션을 로컬에서 처음부터 재생했다. 기본 33개, 학사 33개, 증명 24개, 수납 37개로 **127개 자동 검사**가 통과했다. 수납 검사는 별도 기관 권한, 자기 거래, 원장 직접 접근, 원거래/배분 중복, 동시 좌석/배분/승인, 초과·NULL 금액, 0원 지급, 분할 입금·부분환불·재신청, 기한 만료·늦은 입금, 위임 만료, 결과 불명·미지급·재시도·중복 완료를 확인한다.

브라우저에서 가상 120,000원 신고→대사→전액 배분→수강취소/환불신청→전액 조항 산출→다른 승인자 승인→지급 시작/결과를 저장했다. 마지막 상태는 기지급 120,000원, 청구 조정 120,000원, 예약 0원, 미납 0원이다. 실제 입금·송금은 수행하지 않았다.

타입/린트/프로덕션 빌드와 로컬 DB 보안 점검을 실행했다. 결과 로그는 `../04-report/features/evidence/finance-*.txt`에 보관한다. 개발 캐시에 중복 생성된 `.next/types/* 2.ts` 등이 있어 타입 검사에 충돌했으며 생성물만 재생성해 빌드를 확인했다. 개발 브라우저의 첫 스타일 적용 지연은 재로드 후 정상 CSS 규칙과 화면을 확인했다.

SQL 테스트에서 원거래 참조와 결정 사유의 매개변수/컬럼 이름 충돌을 찾아 명시적 제약조건/함수명으로 해결했다. 지급 함수는 잠금 획득 뒤 승인자 정보를 다시 확인하여 자기 지급 제한을 유지한다. 복구용 기존 무료 과정 함수의 브라우저 실행 권한도 회수해 유료 취소 경로 우회를 막는다.

## 남은 운영 경계

D02/D04/D07 확정, 금융 개인정보 문안·보유기간, MFA/재인증, 모니터링·보존/파기·복구/부하 검증과 운영 배포가 필요하다. 조항 적용은 담당자가 확인하는 방식이고 법률 판정기가 아니다. 실제 계좌 원문은 보관하지 않으며 반환 대상은 기관의 별도 확인 절차를 거친 참조로 남긴다. 현재 화면은 최근 100건이며 장기 회계 보고/페이지 탐색은 후속이다.
