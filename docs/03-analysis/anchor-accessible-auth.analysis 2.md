## 실제 검증

- `verify-accessible-auth.mjs` **21개 통과**: 비밀번호 경계와 실제 로컬 Auth의 가입/로그인/변경 검사. 테스트가 생성한 Auth 계정만 종료 시 삭제한다. 직접 API가 특수문자 없는 값을 허용함을 확인한 항목은 한계 확인이며 보안 충족 점수가 아니다.
- 기존 core **33개 통과**: 인증·역할·신청·강의실 핵심 회귀. 이전 전체270개를 이번에 다시 실행한 것으로 합산하지 않는다.
- 브라우저: 조건2/4→4/4 변경, 버튼·키보드 토글, 서버 거부, 실제 가상 계정 가입, 성공 후 입력/조건 초기화, 과정담당 이메일 로그인 확인. 390px와320px에서 문서 가로 넘침 없음. 페이지 오류 없음.
- lint/production build 통과. 별도 evidence 파일에 결과를 저장한다. DB 스키마 변경은 없다.

## 점검 중 보완

가입 버튼이 이동 링크 옆에 붙어 보이는 것을 모바일에서 발견해 줄을 분리하고 버튼 폭과 글자 크기를 늘렸다. 로그인은 약한 비밀번호로 Auth 세션을 만들기 전에 포털 정책을 검사하도록 정리했다. Supabase 재시작 완료 전에 실행한 첫 API 검사는 서비스 준비 실패로 종료되었으며, 준비 완료 뒤21개 검사를 다시 통과했다. HMR 후 바뀐 브라우저 ref 때문에 처음 가입 클릭이 실행되지 않은 것은 새 ref로 실제 가입을 다시 수행해 확인했다.

TypeScript 빌드의 ES5 target에서 문자열 spread를 허용하지 않아 코드포인트 길이 계산을 `Array.from`으로 수정하고 정책/API 검사21개와 빌드를 다시 통과했다. dev 재시작 첫 방문에서 URL 없는 SyntaxError와 조건 표시 미반응을 확인했으며 재탐색 후 정상 동작했다. 원인을 확정하지 않았다. 빌드된 앱을 실행해 최종 조건4개 충족·비밀번호 숨김·390px 화면·기준 미달 로그인 거부·실제 관리자 로그인→/admin 이동을 별도로 확인했으며 최종 브라우저 오류는 없었다. 초기 개발 세션까지 오류가 없었다고 보고하지 않는다. 현재3100포트는 전용 로컬 Supabase에 연결한 production build 미리보기다.

## 남은 보안·운영 조건

직접 Auth API의 특수문자 강제와 기존 계정 정책 이관이 남아 있다. 길이12자 강제는 신규/변경 비밀번호에 적용되며 기존 약한 비밀번호는 Auth가 소급 차단하지 않는다. 실제 운영 전 재설정·기존 세션 회수·직접 API 경로 보완, 계정 복구, 이메일 인증/SMTP, 관리자 MFA·재인증을 마쳐야 한다. 원격 환경·실제 사용자 자료·외부 문자/이메일/본인확인 업체는 변경하거나 호출하지 않았다.

React 점검: 상태는 입력 컴포넌트 내부에 한정, 조건은 파생 계산, effect는 DOM reset/submit 구독과 cleanup에만 사용, 정책 함수는 client/server 공유, 비밀번호 저장·로그·HTML 삽입 없음, 서버 입력 검증과 기존 역할 검증 유지.
