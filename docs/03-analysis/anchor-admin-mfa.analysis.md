## 검사 결과

신규32개와 기존309개, 총341개 고유 검사 통과. 기존 검사는 계정에 native TOTP를 등록·확인한 후 수행하며 권한 검사나 MFA guard를 비활성화하지 않는다. 일반 학습자 미등록 이용은 신규 검사에서 별도 확인한다.

신규 검사는 AAL1·metadata 우회·타 계정 factor·잘못된 코드·미검증 등록·소비한 challenge 재사용·이전 JWT·실제 시간 만료·refresh·새 인증 이후 오래된 JWT·선택 MFA의 역할 비승격·factor 삭제·이메일 복구·비밀번호 변경·세션 회수·guard 누락을 포함한다.

DB security advisor warn 이상 없음. migration 목록21개와 해당 migration 재적용 확인. 이번에는 기존 자료를 보존하며 전체 DB reset은 반복하지 않았다. lint/build 통과. 브라우저 등록→오류→성공→관리자 업무, 인증 시간 만료→입력 보존→새 창 인증→저장 성공과 모바일을 확인했다.

## 발견·수정

오래된 AAL2 세션으로 native factor API에서 새 앱을 등록한 뒤 그 앱으로 최근 인증을 만들어내는 경로를 확인했다. factor INSERT/DELETE를 별도 DB guard로 보호하고 사용자·세션·작업·대상에 묶인1분짜리 일회용 허가를 추가했다. 만료·타 계정 사용·허가 재사용·오래된 세션의 추가/해제와 관리자 마지막 factor 삭제 거부를32개 검사에 포함했다. 허가/초기 등록 이력 테이블은 RLS와 명시적 권한 회수를 적용했다.

native Auth는 MFA 계정의 이메일/비밀번호 변경에도 AAL2가 필요했다. 기존 이메일 복구를 그대로 두면 관리자 비밀번호 변경에 실패하므로 reset-password 폼과 stateless recovery action에 TOTP 확인 단계를 추가했다. 앱은 인증 엔진의 요구를 우회하지 않는다. 인증 코드가 틀려 이메일 토큰이 소비된 경우 새 메일을 요청하는 안내를 제공한다.

관리자 내려받기에서 감사 이벤트 저장이 최근 인증에 막힐 경우404 대신403과 재인증 안내를 반환하도록 증명·배지 API를 보완했다. 새 보안 페이지의 중복 main landmark도 정리했다.

## 남은 운영 경계

- 실제 직원의 앱 등록 교육·분실 복구 담당/본인 확인 기준·별도 승인자를 기관이 확정해야 한다. 로컬에서 실제 사용자 factor나 비밀번호를 일괄 변경하지 않았다.
- native factor API에도 DB guard를 적용한다. 첫 등록/추가/해제는 현재 사용자·세션·작업에 묶인1분 유효의 일회용 허가를 요구한다. 기존 MFA 계정은 최근 인증 없이는 허가를 받을 수 없고 관리자 마지막 factor 해제는 거부한다.
- 새 public.life_ 테이블에는 guard를 부착하고 검증 스크립트의 누락 검사를 유지한다. service_role/DB 소유자는 별도 신뢰 경계다.
- Auth 내부 session/factor/AMR 스키마와 이벤트 형식은 업그레이드 시 재검증한다. 현재 native TOTP의 시간 허용 오차·시도 제한을 따른다. 소비된 challenge는 재사용할 수 없지만 같은 시간대의 코드를 새 challenge에서 사용할 수 있는 엔진 동작과 구별한다.
- 운영 배포·SMTP·전반적 속도제한·봇 방어·백업/복구·파기 작업·카카오/네이버/PASS는 별도 과제다.
