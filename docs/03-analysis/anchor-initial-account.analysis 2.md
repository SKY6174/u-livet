# 최초 계정 설정 설계 대조

2026-09-19 · [설계](../02-design/features/anchor-initial-account.design.md)

## 범위

초대받은 담당자가 이메일 소유권을 확인하고 처음 비밀번호를 설정하는 기술적 준비를 검증한다. 기관 개인정보 문안 승인, 실사용자 초대, 권한 부여, 공개 가입 개방은 포함하지 않는다.

## 구현 대응

| 설계 항목 | 구현·검증 |
|---|---|
| 초대와 복구 목적 고정 | 각각 서버 액션에서 invite/recovery를 고정하며 조작된 form type·next를 무시 |
| 페이지 조회만으로 인증 소비 금지 | fragment를 화면 메모리로 옮기고 주소에서 제거; verifyOtp는 제출 시 실행 |
| 비밀번호·링크 형식 사전 검사 | 12자 및 대문자·소문자·숫자·특수문자 확인 후 native 검증 |
| 요청 제한 | 기존 reset 요청 제한 적용 |
| 유효·활성 계정만 처리 | native proof, invited_at, life_auth_status 검사 |
| 기존 MFA 보호 유지 | 등록된 TOTP는 올바른 코드가 있어야 변경 허용 |
| 세션 정리 | 완료 시 global logout 및 기존 브라우저 쿠키 삭제; 실패 시 임시 세션 정리 |
| 권한 자동 부여 금지 | 역할 RPC 없음, 관리자 메타데이터를 넣은 합성 계정에도 역할 0개 |
| 친절한 안내 | 큰 입력/버튼, 보이기·숨기기, 조건 체크, 로그인·인증 앱·권한 확인 단계 |
| 기존 복구 유지 | 초대·복구 공통 동작 검사 21개 통과 |
| Supabase 연계 | Preview native 검사 9개 통과, 시험 계정·동의·정책 정리 |
| 배포·템플릿 | Preview 웹 7개 검사 통과; 양 환경 동일 코드 배포 및 한국어 초대 템플릿 반영 |

설계 항목 12개 중 12개 대응(100%). 이는 이 기능의 기술적 준비 범위이며 서비스 전체 개방률이나 법적 적합성 점수가 아니다.

## 검증 결과

- 서버 액션 21개 검사 통과. 토큰 형식, 약한 비밀번호, rate guard, 잘못된 proof, 중단 계정, MFA, native 오류, 로그아웃·고정 이동을 다룬다.
- Preview native 9개 검사 통과. 초대 생성, 목적 분리, 비밀번호 조건, 재사용·만료 차단, 재로그인, 이메일 확인, TOTP 연결을 다룬다. 실제 메일은 발송하지 않았다.
- 수정 TS/TSX lint 및 격리된 체크아웃의 Next.js 빌드·타입 검사를 통과했다.
- Preview 웹 7개 검사 통과. 게시된 코드 버전·초대 페이지, 이메일 미인증 계정, 약한 비밀번호 입력 시 proof 보존, 실제 서버 액션 수락, 재사용 거부, 새 비밀번호 로그인, 이메일 확인을 검증했다.
- 운영 브라우저에서 링크 없는 안내, 테스트 fragment 제거, 비밀번호 입력·조건 안내·보기 버튼 전환, 완료 안내와 계정 보안 로그인 링크를 확인했다. 브라우저에서는 실제 비밀번호를 입력하거나 제출하지 않았다.
- 양 Auth 초대 제목·본문을 적용하고 가입 차단·SMTP·복구 템플릿·비밀번호 정책이 유지됨을 다시 읽어 확인했다. 조회 전용 점검에서 양 DB 계정·승인 개인정보 정책·관리자 0개 및 보호 트리거 활성 상태를 확인했다.
- React 점검: 비밀값을 클라이언트 props로 전달하지 않음, 서버에서 proof·권한 경계 검증, effect 이벤트 정리, 기존 공용 컴포넌트 재사용, 신규 의존성 없음.

## 발견 및 반영

비밀번호 필드에 이전 정책의 ‘대문자나 소문자 중 편한 것’ 안내가 남아 있어 현재 정책과 일치하도록 수정했다. 초대 비밀번호 변경 실패 시 일반 복구 메일을 기계적으로 요구하지 않고 사업단 도움을 안내한다.

Native invite 증명은 비밀번호 설정 전에도 Supabase 세션을 만든다. 앱은 이를 서버의 일시적 클라이언트에만 보관하고 비밀번호 설정 후 종료한다. 이 상태가 비인증이라는 전제는 사용하지 않는다. Supabase native 동작과 앱의 역할 승인을 구분하며, 초대만으로 관리자 권한이 생기지 않음을 실제로 검증했다.

공급자의 유출 비밀번호 검사 등으로 proof 소비 후 비밀번호 설정이 실패할 수 있다. 이때 사업단 도움을 안내하며 완료된 것처럼 로그인 성공을 표시하지 않는다. 실제 담당자 수신함·초대 메일 발송은 검증 범위 밖이다.
