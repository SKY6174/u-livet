# DB 응답 최적화 계획

2026-09-22 · anchor-db-response-optimization

## 목적과 기준

현재 main(930613f)의 운영 DB 연결과 응답을 점검하고, 과정 단위 화면의 불필요한 읽기와 순차 대기를 줄인다. 운영 DB는 uoebygejgglgiivzgyks, 앱은 uc-life.org이며 배포와 DB가 모두 도쿄에 있다. 기존 작업 폴더의 미추적 파일은 보존하고 별도 worktree에서 수정한다.

## 관찰

- DB ACTIVE_HEALTHY, 과정 4개·신청 2개·등록 2개, 현재 배포 READY.
- 운영 HTTP 9회 중 첫 요청 제외 중앙값: health 424.5ms, 과정 목록 266ms, 로그인 138.5ms. 홈은 로그인으로 307 이동하며 이를 로그인 후 성능으로 계산하지 않는다.
- 강사 강의실은 모든 접근 가능한 제출물·성적을 읽고 화면에서 현재 과제만 사용한다. 학습자 강의실도 다른 과정의 읽음·제출·성적을 요청한다.
- 과정 관리 화면은 예산 및 책임강사 조회가 과정 현황 조회를 기다리지만 두 RPC는 현황 결과를 입력으로 사용하지 않는다.

## 범위와 성공 기준

현재 과정에 속한 읽음·제출물·성적만 DB에서 필터하고 기존 5개 읽기의 병렬 실행을 유지한다. 관리 화면의 독립 조회를 함께 시작한 뒤 메모리에서 과정 현황을 결합한다. 기존 권한, RLS, 오류 표시, 폼 동작을 보존한다.

실제 Supabase query builder 및 페이지 실행 회귀검사, 로컬 합성 계정의 네이티브 DB 결과 일치·측정, lint와 빌드를 통과해야 한다. main 반영·push 후 운영 revision, health, 공개 GET을 확인한다. 측정 환경·표본 수를 명시하고 운영 로그인 속도와 로컬 쿼리 비교를 구분한다.

## 제외 범위

운영 자료·계정 설정 변경, DB 스키마/RLS 변경, 전역 사용자 데이터 캐시, 의존성 업그레이드는 포함하지 않는다. Advisor 제안은 실행계획 근거 없이 일괄 적용하지 않는다.
