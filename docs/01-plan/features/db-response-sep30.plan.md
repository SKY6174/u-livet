# 운영 DB 연동·응답 최적화 계획

2026-09-30 · Dynamic

## 현황

- 운영 Supabase 프로젝트는 `ACTIVE_HEALTHY`이고 실제 `life_course_guides` 조회가 성공했다.
- 운영 공개 경로 5회 측정(첫 표본 제외): `/api/health` 중앙값 316.5ms, `/` 145.5ms, `/courses` 282ms, `/auth/login` 139.5ms. 모두 정상 응답이다.
- `pg_stat_statements` 누적 기준 `life_identity()` 1,468회·평균 94.93ms, `life_operation_list()` 221회·평균 458.63ms. 누적 통계는 현재 트래픽의 지연 분포와 다를 수 있다.
- `life_private.identity()`가 `life_private.person_id()`를 직접 호출하고 `member_entry_orgs()` 안에서도 다시 호출한다. 인증·세션 검증의 중복 경로다.
- 로컬 마이그레이션 파일 8개의 버전 번호가 운영 이력의 동일한 이름과 다르므로 CLI dry-run이 중단된다.

## 목표와 범위

- 로그인한 사용자의 공통 신원 조회에서 중복된 `person_id()` 평가를 제거한다.
- 반환 JSON, 회원·관리자 권한, 이메일 확인·동의·세션 유효성 검사를 유지한다.
- 업무 테이블과 RLS, 공개 RPC 계약은 유지한다. `life_operation_list()`는 별도 호출 경로여서 이번 변경에서 건드리지 않고 사후 통계로 추적한다.
- 기존 테스트 계정과 데이터는 변경하지 않는다. DB 검증은 읽기와 롤백 가능한 함수 비교만 수행한다.
- 이력 차이는 해당 8개 SQL 파일의 내용은 그대로 두고 버전 파일명만 운영 이력에 맞춘다.

## 완료 조건

1. 기존 함수와 후보 함수의 JSON을 익명·유효·무효 세션 프로필에서 비교한다.
2. 교차 순서 반복 측정에서 후보의 DB 실행시간이 개선되는지 확인한다.
3. 마이그레이션 하나만 적용하고 함수 정의·권한·헬스 상태를 확인한다.
4. 코드 검사와 빌드, PR 병합, push, 운영 revision 확인까지 완료한다.

## 위험

신원 함수는 보안 경계다. 후보 결과가 다르면 배포하지 않는다. 짧은 반복 측정 결과를 전체 사이트 지연 개선 수치로 일반화하지 않는다.
