## 1. 개요

### 1.1 목적

수강신청원서, 장학금 지급신청서, 수강료 환불신청서를 PDF 작성 도구에서 끝내지 않고 수강생 제출, 담당자 검토, 승인·반려·완료, 처리 이력 확인까지 이어지는 민원형 업무 흐름으로 확장한다.

### 1.2 배경

현재 세 서식은 브라우저에서 입력하고 PDF 1.7 파일로 내려받을 수 있지만, 제출 내용이 서버에 보관되지 않고 관리자가 접수·처리할 화면도 없다. 수강생은 처리 상태를 확인할 수 없고 담당자는 별도 채널로 받은 파일을 수작업으로 관리해야 한다.

## 2. 목표

### 2.1 주요 목표

- [x] 세 서식 모두 PDF 다운로드 기능을 유지한다.
- [x] 수강신청원서는 `입력완료`, 장학금·환불 신청서는 `신청처리`로 제출한다.
- [x] 제출 시점의 PDF 1.7 파일을 변경 불가능한 원본으로 DB에 보관한다.
- [x] 관리자는 조직 범위 안에서 접수 문서를 조회하고 검토·승인·반려·완료 처리한다.
- [x] 수강생은 자신의 문서별 현재 상태와 모든 처리 이력을 확인한다.
- [x] 주민등록번호·서명 등 민감정보는 목록에 노출하지 않고 권한 검증을 통과한 PDF 조회에서만 제공한다.
- [x] 환불 신청은 과정의 등록 수강료와 원본 반환 기준으로 금액을 자동 계산하고 직접 금액 입력을 금지한다.
- [x] 장학금·환불 계좌의 은행은 최신 국내 금융기관 목록에서 선택한다.

### 2.2 비목표

- 실제 계좌 이체, 장학금 지급 실행, 카드 결제 취소 자동화
- 이메일·문자·카카오 알림 전송
- 제출 완료 뒤 PDF 원본의 수정 또는 덮어쓰기
- 서식별 복잡한 다단계 결재선이나 전자결재 시스템 연동

## 3. 범위

### 3.1 포함

- 독립된 문서 신청·처리이력·PDF 원본 테이블과 보안 RPC
- 수강생 제출 동작, 중복 제출 방지, 성공·오류 피드백
- 수강생 처리 현황 및 상태 이력 UI
- 관리자 문서함, 유형·상태 필터, 원본 PDF 열람, 상태 변경과 안내 메모
- 조직·역할·MFA 기반 관리자 권한, 본인 소유권 기반 수강생 권한
- 감사 로그, PDF 무결성 해시, 처리 시 낙관적 잠금

### 3.2 제외

- 기존 `life_applications` 수강 신청 심사 데이터와의 자동 병합
- 외부 문서관리·회계 시스템으로의 자동 전송
- 첨부 증빙 파일 업로드

## 4. 상태와 용어

- `RECEIVED`: 수강생 제출을 서버가 정상 접수한 상태. 수강신청원서 화면에서는 `입력 완료·접수됨`으로 표시한다.
- `REVIEWING`: 담당자가 내용을 확인하고 있는 상태.
- `APPROVED`: 신청 내용이 승인된 상태.
- `REJECTED`: 보완 또는 승인 불가 사유와 함께 반려된 상태.
- `COMPLETED`: 승인 후 실제 행정 처리가 끝난 상태.
- `CANCELLED`: 수강생이 담당자 검토 전 접수를 취소한 상태.

허용 흐름은 `RECEIVED → REVIEWING/APPROVED/REJECTED`, `REVIEWING → APPROVED/REJECTED`, `APPROVED → COMPLETED`이다. 수강생 취소는 `RECEIVED`에서만 허용한다.

## 5. 성공 기준

- [ ] 세 서식에서 최신 입력값으로 PDF 다운로드와 DB 제출을 각각 실행할 수 있다.
- [ ] 같은 제출 키의 재시도는 문서를 중복 생성하지 않는다.
- [ ] 제출 PDF의 헤더가 PDF 1.7이고 다운로드 파일과 동일한 렌더러를 사용한다.
- [ ] 환불 금액은 수업 전 100%, 1/6 전 5/6, 1/3 전 2/3, 1/2 전 1/2, 1/2 이후 0%로 자동 산출된다.
- [ ] 과정 수강료를 확인할 수 없으면 수강료·공제금액·반환액은 공란이고 환불 신청 제출은 안내와 함께 차단된다.
- [ ] 환불 PDF의 중복 신청날짜 칸과 `음영처리된 곳만 표기` 안내 문구가 표시되지 않는다.
- [ ] 수강생 A는 수강생 B의 신청 목록·이력·PDF를 볼 수 없다.
- [ ] 권한 없는 사용자와 MFA 미확인 담당자는 관리자 목록·처리 RPC를 사용할 수 없다.
- [ ] 관리자 상태 변경마다 이전/이후 상태, 담당자, 안내 메모, 시간이 기록된다.
- [ ] 반려 처리에는 안내 메모가 필수이고 동시 수정은 revision 검증으로 차단된다.
- [ ] 수강생 화면은 새로 고침 뒤에도 접수 현황과 처리 이력을 표시한다.
- [ ] 타입 검사, 린트, 빌드, DB 회귀 검증, 브라우저 제출 흐름이 통과한다.

## 7. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 주민등록번호·서명 포함 PDF 노출 | 높음 | private schema에 bytea로 저장하고 SECURITY DEFINER RPC에서 소유권·역할·MFA를 검증한다. 목록 응답에는 민감정보를 포함하지 않는다. |
| 제출 중 네트워크 재시도로 중복 접수 | 중간 | 수강생별 request key 유일 제약과 idempotent RPC를 사용한다. |
| 관리자가 오래된 화면에서 상태 덮어쓰기 | 중간 | revision 기반 낙관적 잠금으로 거부하고 최신 목록을 다시 불러오게 한다. |
| 큰 서명 이미지로 DB·요청 과부하 | 중간 | 서버에서 원본 PDF를 다시 생성하고 PDF 크기 상한을 검증한다. |
| 회계 지급 완료로 오해 | 중간 | `APPROVED`와 `COMPLETED`를 분리하고 자동 지급은 범위에서 제외한다. |
