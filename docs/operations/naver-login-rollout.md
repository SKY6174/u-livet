# 네이버 로그인·개인정보 안내 적용 기록

확인일: 2026-09-22 KST.

## 후속 수정: 최초 가입과 재로그인 연결

초기 기록 아래의 이메일 확인 안내 방식은 이 수정으로 대체한다.

- 이용자의 실제 시도에서 네이버 identity는 생성됐지만 Auth의 로그인 이메일·confirmation_sent_at·last_sign_in_at은 비어 있었다. 연락처 이메일도 이용자가 원하는 네이버 메일 주소와 달랐다. 발송 여부가 확인되지 않은 채 인증 메일을 보냈다고 안내한 것이 오류였다.
- 네이버 제공자 `email_optional=true`와 가입 화면의 이메일 확인을 함께 사용한다. 가입 대기 세션은 네이버의 안정적인 회원 식별자로 연결하고, 이용자가 직접 입력한 이메일만 Auth 이메일 확인 후 계정에 등록한다. 공급자 이메일의 확인 상태를 true로 조작하지 않는다.
- 기존 이메일이 없는 네이버 회원에게 이메일 요청·인증번호 입력 화면을 제공한다. 메일 발송 실패는 성공으로 안내하지 않는다. 인증된 사용자/가입 대기 상태/대기 이메일/반환 사용자 ID를 모두 검사한다.
- OTP 세션은 별도 무저장 클라이언트에서 검증 후 폐기하고 원래 OAuth 세션을 갱신한다. 가입 완료 뒤 재로그인은 같은 네이버 identity에 연결된다.
- `20260922013214_anchor_naver_signup_email.sql`을 운영에 적용했다. DB 직접 호출도 확인된 이메일 없이는 가입할 수 없다. 합성 사용자·OAuth 세션으로 미확인 이메일, 위조 metadata, 동의 누락 차단과 가입 완료·중복 제출·역할 미부여를 검증한 뒤 전체 트랜잭션을 rollback했다.
- 운영 이메일 변경 템플릿에 인증번호를 추가했다. 현재 Auth 숫자 코드 길이는 8자리이며 전역 자동 이메일 확인, 미확인 이메일 로그인 허용, 보안 이메일 변경 설정은 그대로다.
- 가입 복귀 주소 `https://uc-life.org/auth/complete-signup**`를 허용 목록에 추가했다. OAuth 오류에도 수강생·교외 대상과 QR 복귀 경로를 유지한다.
- 가입 연결 회귀 27건과 기존 어댑터·로그인 대상·카카오·자동 분기 검사가 통과했다. 실제 가입 컴포넌트의 이메일 확인 전/후 화면을 로컬 브라우저로 점검했다. 이 결과는 개인 계정의 이메일 확인과 이용 동의를 대신하지 않는다.
- 개인정보 v6: `11dea455-7125-4bba-a8b5-a919ff6d59e3`, `2026-09-22T01:35:29.816609Z`, 본문 SHA-256 `23a0f9280399d5588d3e59082f8c8f3cad360f50ca6bf8d5a7ac6a76c1ede71e`. 직접 입력한 이메일과 네이버 연락처의 차이를 설명한다. 기존 문안·동의 7건은 보존했다.
- 이용자가 원하는 이메일이나 동의·수강 상태를 관리자로 강제 지정하지 않았다. 다음 네이버 인증 후 가입 화면에서 본인이 선택한 주소를 입력·확인한다.
- 수정 코드 `a6148713820ab042ea61a9661c5591511145d78a`, 배포 `dpl_911gnkx329bQNACAPrbMYEZiGeXd`가 READY이고 운영 버전이 일치했다. 이후 네이버 provider의 `email_optional=true`를 적용했고 2026-09-22T01:39:56Z의 새 flow state에 반영된 것을 확인했다.
- 운영에서 과거 이메일 확인 오류 주소를 열어도 수강생 로그인과 활성 네이버 버튼이 표시된다. 개인정보 v6 노출도 확인했다. 개인 계정의 인증번호 입력·가입 완료는 사용자 확인이 남아 있다.

## 요청 및 적용 범위

사용자가 네이버 검수용 실제 로그인 연결과 git push를 요청했고, 이어 “개인정보 보호 규칙에서 네이버 관련 내용을 추가해줘.”라고 지시했다. 이 요청에 따라 네이버 항목을 추가했다. 별도의 최종 문안 승인 응답을 받은 것으로 기록하지 않는다.

- 운영 Supabase `custom:naver`의 기존 Client ID/Secret과 PKCE 설정을 유지했다.
- 사용자 정보 URL을 `https://uc-life.org/api/auth/naver/userinfo`로 바꾸고 `sub`/`email`만 매핑했다. scope와 추가 claim 허용 목록은 비어 있다.
- `email_verified`는 Supabase 보호 필드이므로 attribute mapping에 넣지 않는다. 네이버 응답은 확인 상태를 제공하지 않아 어댑터가 false를 반환하고 기존 이메일 확인 설정을 유지한다.
- 운영 Vercel `AUTH_NAVER_ENABLED=true`를 설정했다. 이 값은 새 배포부터 적용된다.
- 실제 Supabase 인가 응답은 네이버 `/oauth2.0/authorize`로 302, 빈 scope, state 및 PKCE 포함, callback `https://uoebygejgglgiivzgyks.supabase.co/auth/v1/callback`이다.
- 스테이징의 네이버 연동·문안은 이번 작업에서 변경하지 않았다.

## 복구

네이버 오류가 발생하면 운영 `AUTH_NAVER_ENABLED=false`로 재배포해 기존 로그인 수단을 제공한다. 사용자 계정·동의 기록·정책 문안은 삭제하거나 이전 내용으로 덮어쓰지 않는다. 네이버 Secret 변경은 이번 작업에 포함되지 않았다.
