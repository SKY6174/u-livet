# 공개 가입 및 최초 관리자 설정 순서

2026-09-19 · 현재: 준비 점검 완료 / 공개 가입 미개방

## 현재 상태

마지막 준비 점검에서 운영과 Preview 모두 Auth 계정 0개, 승인된 ACCOUNT_PRIVACY 0개, 초기 관리자 0명이었다. 메일 연결은 완료됐고 native 공개 가입은 꺼져 있다. 가입 화면·server action·DB 트리거는 승인 문안과 동의를 확인한다. 앱 공개 가입도 `AUTH_SIGNUP_ENABLED=false`로 차단한다. 운영 Supabase 리전은 도쿄다. 동일 코드 배포와 메일 복구 검증은 [메일 보고서](../04-report/features/anchor-primary-domain-mail.report.md)를 참조한다.

관리자 후보의 실명·이메일·문의 연락처는 `ops/evidence/signup-opening/`의 비공개 검토본에 기록한다. 확정된 업무용 문의 번호를 공개 문안에 사용하고 개인 휴대전화는 별도 공개 승인 없이 게시하지 않는다.

## 1. 기관 문안 확정

[개인정보 검토 틀](privacy-review-template.md)을 기준으로 처리자 법적 명칭, 업무별 수집 항목/근거, 보유기간, 문의 담당자, 위탁·국외이전 내용을 확정한다. 승인본의 버전·시행일·승인자·승인 근거와 본문 해시를 비공개 운영 기록에 남긴다. 학교의 일반 홈페이지 방침을 이 서비스의 승인본으로 자동 대체하지 않는다.

개인정보 처리방침 게시와 수집·이용 동의는 목적이 다르다. 현재 UI가 같은 ACCOUNT_PRIVACY 본문을 재사용하므로, 가입에 대한 필수 수집·이용 절과 그 밖의 처리 안내를 분리해 설명해야 한다. 선택 홍보·강사 공개·배지 공개 및 별도 국외이전 동의가 필요한 경우에는 각각 독립된 수단을 준비한다. 새로운 필수 동의가 필요하면 현재 한 개 체크박스로 개방하지 않는다.

## 2. 최초 정책 승인자 등록

`life_policy_versions.approved_by`는 `life_people.id`를 참조한다. 실제 기관 승인 근거가 확보된 경우, 그 승인자의 업무상 식별 행을 먼저 등록하고 승인 정책을 연결할 수 있다. Auth 계정이 없어도 가능하다. 이 행에는 로그인 연결이나 업무 권한을 부여하지 않는다.

초안 자동 승인, 가상 승인자 사용, 승인 트리거 해제는 하지 않는다. 승인 정책은 동결되어 있으므로 잘못된 내용을 덮어쓰지 않고 버전 관리 절차를 따른다. 동시에 유효한 정책이 여러 개면 현재 UI에서 과거 버전도 선택·조회될 수 있으므로 교체 설계를 확인한다.

## 3. 최초 담당자의 본인 동의와 계정 설정

담당자 지정, 기관 문안 승인, 당사자의 개인정보 동의는 세 가지 별도 증거다. 이름·이메일을 받았다는 사실로 `privacy_accepted=true`를 생성하지 않는다.

현재 `handle_new_user`는 Admin API를 통한 생성에도 승인 문안과 동의를 요구한다. 일반 `inviteUserByEmail` 호출만으로 가입 전 동의 문제를 해결할 수 없다. 승인된 문안을 당사자에게 실제로 보여주고 해당 버전에 대한 동의 및 초기 설정 메일 발송 요청을 받은 뒤, 비공개 초기 계정 설정 절차를 수행한다.

계정 생성 전에 정확한 프로젝트·대상 이메일·문안 버전·동의 일시·계정 생성 방식·발송 방법을 정한 실행안을 검토한다. 비밀번호 원문을 채팅·Git·로그로 주고받지 않는다. 이메일 소유권 확인을 생략하는 `email_confirm=true`를 편의상 사용하지 않는다. 운영 담당자가 승인된 링크에서 직접 비밀번호를 설정한다. 기존 가입 트리거의 동의 `source='SIGNUP'`만으로 외부에서 받은 초기 동의의 출처를 설명할 수 없으므로 그 실제 증거를 비공개 운영 기록에 함께 남긴다.

초기 설정은 `/auth/accept-invitation`에서 처리한다. [한국어 초대 템플릿](../../supabase/templates/invite.html)은 각 환경의 SiteURL로 연결한다. 링크를 열기만 해서는 인증을 소비하지 않고, 비밀번호 조건을 확인한 뒤 제출할 때 native invite proof를 검증한다. 성공 후 세션을 종료하고 새 비밀번호 로그인 → 인증 앱 연결 → 업무 권한 확인을 안내한다. 링크는 15분·1회 사용이며 만료 시 사업단에 새 초대를 요청한다.

발송은 승인 문안과 본인 동의 증거를 확보한 뒤 비공개 운영 절차로 실행한다. 화면에는 초대 발송 기능이나 역할 자동 부여 기능이 없다. 공개 가입을 잠깐 열어 관리자 한 명만 가입시키는 방식도 사용하지 않는다. Preview 합성 계정으로 검증하며 실제 초대 메일의 수신 확인은 별도다.

## 4. MFA와 권한

이메일 확인·본인 비밀번호 설정 후 `/auth/security`에서 인증 앱을 연결한다. 현재 12자 이상 및 영문 대문자·소문자·숫자·특수문자 정책을 적용한다. 권한 승인은 사람·조직·역할·적용기간 단위로 기록한다.

| 역할 | 용도 | 최초 부여 기준 |
|---|---|---|
| SYSTEM_ADMIN | 시스템 운영자 식별, 관리 보안 절차 | 지정된 시스템 담당자 |
| COURSE_MANAGER | 과정·수강·운영 관리 화면 및 해당 업무 | 과정 운영을 맡는 담당자 |
| FINANCE | 수납·환불 업무 | 회계 담당 지정 시 |
| CERTIFIER | 증명 관련 업무 | 별도 발급 권한 및 위임 확인 시 |
| PERFORMANCE | 연차 성과 업무 | 성과 담당 지정 시 |

SYSTEM_ADMIN 하나가 모든 업무 역할을 포함하지 않는다. 최초 담당자가 과정 운영도 맡는다면 두 역할의 부여 범위를 명시적으로 정한다. 임의로 전 역할을 부여하지 않는다. 재로그인 후 AAL2와 최근 인증 상태, 관리자 화면 접근, 승인되지 않은 회계·증명 업무 차단을 확인한다.

## 5. 개방 전 확인

1. `ops/signup-readiness.sql`을 운영·Preview에 각각 읽기 전용으로 실행한다. 개인정보 원문 대신 건수·불리언만 저장한다.
2. 실제 승인 문안이 공개 화면과 가입 화면에 맞게 표시되는지 확인한다. 필요한 추가 동의·국외이전 안내, 민원·파기 처리 창구가 준비돼야 한다.
3. 지정된 테스트 수신자에게 발송 승인을 받고 가입 인증 및 복구 메일의 받은편지함·스팸함·발신자·링크를 확인한다. Resend 진단 주소 Delivered는 이 단계의 대체 증거가 아니다.
4. 최초 담당자 설정을 Preview에서 검증하고 운영 적용 후 MFA 및 역할 접근을 확인한다.
5. 제한된 시험 가입 → 이메일 인증 → 로그인 → 기본 학습자 권한 → 동의 버전 기록을 검증한다. 역할 메타데이터로 관리자 권한을 얻지 못해야 한다.
6. 담당자 승인 후 개방 작업 시간에 운영 native 공개 가입을 활성화하고 Vercel 운영의 `AUTH_SIGNUP_ENABLED=true`를 설정·재배포한다. 두 조건과 승인 문안·메일 준비가 모두 있어야 가입할 수 있다. 웹 가입 흐름과 동의 저장까지 확인한다. 실패하면 native 공개 가입을 즉시 중단하고 앱 설정도 false로 재배포한 뒤 이미 접수된 사람의 처리 상태를 확인한다.

`AUTH_SIGNUP_ENABLED` 누락·false·잘못된 값은 공개 가입 차단이다. 로컬 시험에서도 공개 가입을 시험할 때만 명시적으로 true를 사용한다. 이 값은 이미 발급된 초대 수락, 로그인, 비밀번호 복구를 중단하지 않는다. 최초 담당자용 정책을 등록했다는 이유로 앱 공개 가입을 함께 켜지 않는다.

DB 점검 결과는 법적 승인·메일 실수신·실제 MFA 로그인·공개 가입 허가를 판정하지 않는다. 환불·감면·강사 심사·증명 발급 권한은 각 승인 기준에 따라 별도 개방한다.
